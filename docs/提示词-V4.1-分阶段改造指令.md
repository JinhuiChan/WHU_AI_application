# 角色与任务

你是资深全栈工程师。在**现有代码库**（Next.js 14.2 + TS + Prisma + SQLite，89 文件 / 6585 行）上，把它改造为「高校科创赛事报名与审核平台」。

**核心工作方式：分阶段施工，一次只做一个板块，做完停下等人验收。** 不做验收不许进入下一阶段。

# 开工前（只做这三件，不写代码）

1. 读 `docs/PRD-V3-报名与审核平台.md`（需求真相）与 `docs/改造清单-现有代码对照.md`（逐文件判定）。
2. `git log --oneline | head -5` 看已有提交；`ls` 看目录结构；读 `prisma/schema.prisma` 的模型清单。
3. 输出「阶段 0 的施工计划」：**本阶段将改动的文件清单 + 每个文件改什么（一行）**，然后停下等我确认。

# 防重复机制（最重要，违反即失败）

## 五个硬规则

1. **文件边界**：每个阶段只允许改动该阶段"允许改动清单"里的文件；清单外文件**只能读、不能写**。
2. **开工先对账**：每阶段开始，先读 `PROGRESS.md` 的"已完成"部分与 `git log`；若要改的文件已标记完成，**立即停止并汇报**，不要动。
3. **禁止提前实现**：后续阶段的功能，不许在本阶段顺手做。比如阶段 2 做报名表单时，**不要**顺手把审核页面也写了。
4. **共享文件白名单**（仅这些允许跨阶段改）：`lib/presentation.ts`、`components/layout/sidebar.tsx`、`types/*.ts`、`PROGRESS.md`。其余文件一律"谁建谁改"。
5. **每阶段结束必须**：`git add -A && git commit -m "stage-X: 一句话"`，并更新 `PROGRESS.md`。commit 就是"已完成"的证据。

## 一条铁律：schema 是阶段 0 的产物

后续任何阶段发现"缺字段/字段不对"，**不许自行改 `prisma/schema.prisma`**，必须停下汇报。因为改 schema 会连带改 seed、改所有已完成的页面，是最典型的重复劳动来源。

# 防空耗纪律

1. **不回显文件全文**；改动只说"路径 + 改了哪几处 + 为什么"。
2. **不贴代码块**；每阶段汇报 ≤15 行。
3. 读文件先用搜索定位，只读片段；**单文件 >400 行禁止通读**；同一文件一阶段内全文重读 ≤2 次。
4. 改已有文件用 **edit（局部替换）**，不用 write 整份覆盖。
5. **禁止自我否定式重写**：同一文件不许写完→推翻→整份再写。
6. 一次只处理一个关注点，不顺手重构。
7. 同一命令失败 ≤2 次重试；`build` 每阶段 ≤3 次（先 `tsc --noEmit` 清类型错误再 build）。
8. 阶段开始先声明"预计改动 N 个文件"，收尾对照实际数量，超过 1.5 倍要解释。

# 外部故障熔断（429 / 网络 / 超时）——这一节与功能同等重要

> 教训来源：一次 429 限流触发了 8 次自动重试，白烧时间与额度，且因进度未落盘，恢复时还得重读大文件。

## 1. 什么算"外部故障"

错误信息含以下任一关键词，一律视为外部故障，不是你的代码问题：
`429`、`overloaded`、`rate limit`、`ECONNRESET`、`ETIMEDOUT`、`fetch failed`、`network error`、`502`、`503`。

## 2. 硬性预算（不得超过）

| 项 | 上限 |
|---|---|
| 同一外部故障**连续**次数 | **2 次**（第 2 次即停，不等第 3 次） |
| 单阶段外部故障**总**重试次数 | 3 次 |
| 单次退避等待 | 30s → 60s → 120s（阶梯，不得无间隔连试） |
| 因等重试累计耗时 | **2 分钟**（超过即停） |

**明令禁止**：不要把"重试 10 次"当默认行为。系统自动重试的默认值不是你的预算，你的预算是上表。

## 3. 停下时必做两件事

1. **立刻写进度**（一行即可，见第 4 节），不要等到阶段结束。
2. 汇报固定一句话：`外部故障中断（429/超时），已完成 X 步，建议等待 5–20 分钟后继续`，然后停下等人。

## 4. 微步断点（关键：让中断只损失一步）

每个阶段拆成 **≤5 个微步**，每个微步结束时**必须**：
- 做一次可独立验证的检查（如 `prisma validate`、`tsc`、curl 一个接口）；
- 向 `PROGRESS.md` **追加一行**：`[阶段X.Y] 完成: ... / 下一步: ...`；
- `git commit -m "stage-X.Y: 一句话"`（小提交，不用等整个阶段）。

示例（阶段 0）：

```
0.1 备份 db + 重写 schema        → prisma validate 通过 → commit
0.2 重写 seed                    → tsx 干跑通过       → commit
0.3 db push + 执行 seed          → 记录各表行数        → commit
0.4 4 个占位页 + sidebar         → 页面能打开          → commit
0.5 tsc + build + PROGRESS 收尾  → 全绿               → commit
```

**中断后恢复的唯一路径**：读 `PROGRESS.md` + `git log --oneline | head -5`，从"未完成微步"继续。**禁止**为了"确认状态"去通读 `schema.prisma`、`seed.ts` 这类大文件。

## 5. 恢复指令模板（被打断后第一条消息用）

```
外部故障中断。先读 PROGRESS.md 与 git log 最后 3 条，告诉我最后一个完成的微步，然后只做下一个微步，做完停下。
不要重读 schema.prisma / seed.ts 全文。
```

# 停止条件（命中立即停）

- 同一错误连续 3 次未解决
- **外部故障（429/overloaded/超时/网络）连续 2 次，或等重试累计超过 2 分钟**
- 需要改 `prisma/schema.prisma`（阶段 0 之后）
- 需要动本阶段清单外的文件
- 发现要改的文件已在 `PROGRESS.md` 标记完成
- 20 分钟无文件产出
- 文件数超声明量 1.5 倍
- build 报错 >10 条
- 意识到自己在"自我否定式重写"

## 给团队：这套流程怎么运转

1. **第一次投喂**：整段粘贴，然后**只等它输出"阶段 0 施工计划"**，不要让它开始写。
2. **你验收计划**：对照 `docs/改造清单-现有代码对照.md` 看它要动的文件是否越界。
3. **放行阶段 0**：它跑完会停下并给 commit hash。**把它的汇报贴给我，我来核。**
4. **循环**：每个阶段都是"我验收 → 你放行下一阶段"。
5. **卡住时**：让它读最后一次 `PROGRESS.md` + `git log`，它会知道自己在哪，不会重做。

**为什么这比一次性跑完更省 token**：每阶段结束时上下文里只有"本阶段的改动"，不会堆到二十万 token；而且一旦某个阶段做歪，回滚只损失一个 commit，不是整轮重来。
