## 1. 定目标

### 1.1 一句话目标

> **在"不重复建设"的前提下，为全校科创赛事建立一本可追溯、可解释、可导出的权威成绩账本，并把两套现有平台（第二课堂、青创珈X）与线下 Excel 的数据统一到一个以"项目"为主键的视图上；同时用 AI 承接重复性咨询与作品提交前的规范性诊断，把老师和学长的时间释放出来。**

### 1.2 成功标准（可核查）

| 编号 | 标准 | 核查方式 |
|---|---|---|
| S1 | 一个项目从报名到获奖的全貌，能在**一屏内**呈现（含成员变更历史） | 现场演示：任选 1 个历史项目，3 次点击内到达全貌页 |
| S2 | 获奖台账的每条记录都带**证据链**（来源链接/文件 + 核验人 + 核验时间） | 随机抽 20 条，逐条可点开佐证 |
| S3 | 人员变更可追溯：任一项目可回放其每次人员变更前后的成员构成 | 抽 5 个跨赛段项目验证 |
| S4 | 数据质量可度量：系统自动标红的异常有处置结论，**处置率可统计** | 看板「数据质量」页展示处置率 |
| S5 | AI 咨询回答**必带出处**（文件名 + 章节 + 生效赛年），无出处时降级为转人工 | 抽 20 组问答核验出处真实性 |
| S6 | 材料检查的每条结论可回溯到规则条款或评分细则条目 | 抽 10 条结论，逐条指认依据 |
| S7 | 断网环境下，账本、看板、材料规则检查 **100% 可用** | 物理断网演示 |
| S8 | 系统可一键迁回校内环境 | 预演环境完整跑一次"导出—迁移—切换" |

### 1.3 交付物

1. 本 PRD 文档（含功能清单、数据模型、验收标准）
2. 可运行系统：管理后台工作台 + 学生端 + 数据看板
3. AI 智能体：站内咨询 + 材料规范性检查/分维度诊断
4. 演示脚本与历史数据迁移样本（用于答辩）
5. 部署与迁移手册（云上运行 + 校内迁回步骤）

### 1.4 给谁看、谁去用

- **看的人**：发榜方评审专家（校团委/赛事办）、学校分管领导、指导教师。
- **用的人**：赛事办管理员（日常主用户）、学院团委/教务联络人、指导教师、参赛学生、学院领导（只读看板）。

## 2. 背景与问题定义

### 2.1 现状（来自榜题原文的复述与拆解）

科创赛事（中国国际大学生创新大赛、挑战杯、百珈争创等）的通知与时间节点、团队在校赛/省赛/国赛的人员变更、获奖台账、各类统计表单、赛事数据看板、作品提交前的规范性检查与打磨反馈——**全部没有平台支撑**，仍靠群通知、Excel 与人工比对。

数据分散在三处：

| 数据 | 所在位置 | 问题 |
|---|---|---|
| 报名、网评 | 第二课堂综合管理平台 | 有系统，但只能看自己那一段 |
| 组队招募 | 青创珈X 平台 | 有系统，与报名数据不互通 |
| 获奖与统计 | Excel + 线下表格 | 无权威源、口径不一、无法追溯 |

### 2.2 四个真实痛点（榜题"最费时最易出错"的转译）

1. **P1 数据分散**：想看一个项目从报名到获奖的全貌，要跨三套系统比来比去。
2. **P2 获奖统计易错**：同一项目在校赛、省赛、国赛的成员和指导老师常有调整，人工比对常对不上。
3. **P3 规则咨询重复**：赛事规则、评分细则、商业计划书与路演 PPT 要点被反复询问，老师与学长要一遍遍回答。
4. **P4 材料核验全人工**：提交前的格式与内容一致性核验全靠人看，耗时长、口径不一致。

### 2.3 三个学科视角（为什么这样设计，而不是那样）

这份方案在三个层面同时成立，才会被真正采用：

- **信息架构视角**：痛点的本质不是"缺一个系统"，而是**缺一个统一主键**。三个系统各自以"报名号""队伍号""Excel 行号"为标识，所以永远对不上。本方案的核心动作是引入**"项目"作为唯一主数据**，其余全部挂靠。这是整份文档的技术地基。
- **组织行为视角**：一旦台账绑定学院考核与教师工作量，报数方就有动机优化数字（Goodhart 定律）。因此系统不能只做"记录"，必须同时做**异常标红 + 处置留痕**，让"数字来源"本身可审计。这也是 Q9 选择"记录 + 自动标红"而非"建审批流"的原因：前者治的是"发现不了"，后者治的是"批不批"，而真实痛点在后者之前。
- **公共管理视角**：校级系统的合法性来自"权威口径"。因此 Q10 选择"主办方公示为准"，而不是"团队自报"，目的是让这本账在争议时有且只有一个裁判。

### 2.4 不做重复建设的原则

本方案**不重造**报名与网评（第二课堂在做）、**不重造**组队招募（青创珈X 在做）、**不重造**评审打分。系统的角色是：

> 一个**聚合与治理层** + 一个 **AI 能力层**，而非第三个平行业务系统。

## 3. 产品定位与边界

### 3.1 定位

**双端并重的"赛事数据中枢 + AI 助手"**（决策 Q1-C）：

- **管理侧（工作台 + 看板）**：跨平台数据聚合、获奖权威台账、人员变更追溯、数据质量治理、学院视角统计。
- **学生与教师侧（AI 助手）**：站内规则咨询、材料提交前的规范性检查与分维度诊断。

两端的共同主键是"项目"，同一套数据、两种视角，不各建一套。

### 3.2 能力地图（首期 vs 二期）

```
                ┌──────────────────────── 首期（V1 + V2）────────────────────────┐
数据层   数据接入(接口/导入/补录) → 主数据对齐 → 质量治理(标红/待核实池) → 权威台账
展示层   总览看板 / 学院排行 / 项目全貌 / 数据质量页
AI 层    站内咨询(带出处) / 材料规范性检查 / 分维度诊断(短板排序)
                └──────────────────────────────────────────────────────────────┘
                ┌──────────────────── 二期（V3）过程模块 ──────────────────────┐
过程层   通知与节点聚合 / 组队招募聚合 / 自定义表单引擎 / 推荐上报 / AI 打磨反馈
                └──────────────────────────────────────────────────────────────┘
```

> **术语校准**：Q7「只管赛后」= 首期范围，不是产品终局（Q8-A）。Q19 的 V1/V2/V3 是首期内部的技术里程碑（V1 账本底座、V2 AI 能力、V3 过程模块）。即：**首期 = V1 + V2；过程模块 = V3**。

### 3.3 明确不做（排除项）

| 不做 | 理由 |
|---|---|
| 报名与网评功能 | 第二课堂已在做，重造即冲突 |
| 评审打分、评委分配、排名计算 | 评审规则由主办方掌握，系统只消费结果 |
| 学分认定、教师工作量认定 | 跨部门工程，系统只提供**导出接口**，不做认定 |
| 电子证书签发、荣誉墙 | 二期后再议，首期不投入 |
| 独立原生 App | 学生端做响应式移动优先，管理端桌面优先 |
| 对外商业收费 | 首期校内免费、无内购；多校复制为二期可议价输出 |

### 3.4 红线（触碰即停）

1. **不得出现无法回溯的数字**：任何进入看板的统计值，必须能下钻到原始记录。
2. **不得让 AI 输出无出处的结论**：咨询类无出处即转人工；诊断类无条款依据即不出结论。
3. **不得把"AI 诊断"表述为"评审结论"**：界面与文案层面禁止出现分数预测、名次预测。
4. **不得让个人敏感字段对普通用户开放**：手机号、身份证、银行卡等字段永久遮蔽。
5. **不得在未发布前泄露赛事结果**：结果默认仅管理员可见，需显式"发布"动作。

### 3.5 截止线（做到哪一步即算完成）

首期完成 = V1 与 V2 全部 P0 需求可演示 + S1–S8 验收标准通过 + 一次真实赛事跑通并留有使用记录。V3 过程模块不在首期截止线内。

## 4. 目标用户与场景

### 4.1 角色与权责（决策 Q3-D 极简制）

| 角色 | 典型人数 | 核心诉求 | 权限要点 |
|---|---|---|---|
| 系统管理员（校级） | 1–3 | 数据权威、全校总账、对外报数 | 全部数据读写、结果发布、账号审核 |
| 普通用户（学院管理员/教师/学生） | 全校 | 查自己的、查本院的、问规则、交材料 | 数据**默认全校可见**；仅内部赛与未发布结果受白名单限制 |

极简制的两条补偿设计（已定，不需再议）：

- **结果发布开关**：赛事结果默认"仅管理员可见"，一键发布后对默认可见生效。
- **字段级遮蔽**：手机号、身份证号、银行卡号等字段永久不对普通用户开放，管理员亦仅可见脱敏值。

> 风险备注：极简制以"配置成本低"换"精细授权能力"，一旦出现跨院敏感数据争议（如未公开的评审意见、企业命题赛的商业计划书），只能靠白名单硬编码应对。此风险列入第 12 章待确认事项。

### 4.2 五个典型场景

**场景一：赛事办老师做年度总结**
12 月底要报一份"本年度科创赛事成果"给校领导。过去：翻 3 个系统 + 5 个 Excel，口径要自己统一，改一版要重做一遍。现在：看板选"赛年 2026"，勾选"仅统计省赛及以上"，导出一页 PDF；每个数字都能点开看是哪些项目。

**场景二：学院老师核对本院获奖**
学院只会关心本院的账。过去找赛事办要表，现在直接进"学院视角"，看到本院 37 个项目的获奖明细，导出后与学院自己留的底账对一遍——不一致的地方，点进项目全貌看证据链，直接定位是哪条通道（api/import/manual）进的数。"

**场景三：项目成员变更的追溯**
某项目校赛 3 人、省赛 5 人（新增 2 人）、国赛指导老师更换。评审质疑"临时加人"。管理员打开项目全貌的"版本时间线"，回放到省赛版本，看到变更是 3 月 12 日经学院提交、赛事办确认，附有变更说明。**系统不说"批没批"，只说"何时、由谁、改了什么、有无佐证"**——这恰好是争议时最需要的。

**场景四：学生问"商业计划书要写几页"**
学生在站内问 AI。AI 答："按《2026 年 XX 大赛参赛手册》第 4 章第 2 节，商业计划书建议 15–20 页，需包含市场分析、商业模式、财务预测、团队介绍、社会价值五部分（出处：参赛手册.pdf · 第 12 页 · 适用赛年 2026）。" 若无匹配，答："该问题暂无权威口径，建议联系赛事办刘老师 027-68775751。"

**场景五：提交前自查**
学生上传路演 PPT，系统检查：页数 22 页（规则上限 20 页，✗）、缺少"财务预测"章节（✗）、全文出现"我们大概是行业第一"等 3 处无数据支撑的表述（⚠）。诊断页给出短板排序：①财务预测缺失 ②创新性论证偏弱 ③社会价值表述笼统。**不给分、不预测名次。**

## 5. 功能需求（分模块）

需求优先级：**P0** = 首期必须；**P1** = 首期尽力；**P2** = 二期（V3）。

### 5.1 M1 数据接入与主数据管理（P0）

**目的**：把三处数据统一成一套标准模型，且任何一条数据都能说清"从哪来、什么时候来的、谁确认的"。

**FR-1.1 三通道接入（决策 Q4-D 分层降级）**

| 通道 | 触发方式 | 实时性 | 适用 |
|---|---|---|---|
| 接口通道 `src=api` | 定时任务 / Webhook | T+0 ~ T+1h | 对方开放 API 时 |
| 导入通道 `src=import` | 管理员上传 Excel/CSV，模板校验后入库 | 手动触发 | 对方可导出但不开放接口 |
| 补录通道 `src=manual` | 管理员表单逐条录入 | 即时 | 两平台都没有的历史数据 |

- 优先级瀑布：接口 > 导入 > 补录；同一实体多来源时，以**最近一次成功同步**为准，旧值进历史表。
- 每条记录强制携带：`source_type`、`source_ref`（接口 URL / 文件名 / 录入人）、`synced_at`、`batch_id`。
- **验收**：任选一条获奖记录，可展示其来源类型、来源标识、同步时间、批次号。

**FR-1.2 导入模板与校验**

- 提供三类标准模板：项目信息、获奖记录、人员名单。
- 导入前校验：必填字段、学号格式、赛事名称与赛年匹配、团队人数上下限、重复行检测。
- 校验失败**不整批回滚**，逐行报错并支持"仅导入通过行"，错误行导出后修正再传。
- **验收**：构造一份含 5 类错误的 100 行文件，系统能逐行指出错误原因并导入其余有效行。

**FR-1.3 主数据对齐（决策 Q5-D）**

- **项目**为唯一主数据：`project_id`（系统生成，永不变更）+ 别名表（兼容各平台的项目名、报名号、队伍号）。
- **身份**以"学号/工号"为主键（决策 Q15 修订：首期自建账号库，预留 `external_id` 供将来对接统一身份认证）。
- 同一人被多处引用时，以学号归并；姓名不同但学号相同 → 视为同一人并提示核对；学号不同但姓名相同 → **不自动合并**，进异常池。

**FR-1.4 赛年独立字段（决策 Q17-A 的专项设计）**

- `competition_year` 为准入统计的唯一依据，**禁止从日期推断**（省赛常跨年：12 月报名、次年 5 月获奖）。
- 赛事字典表中，同一赛事的不同届次存为不同实体，届次间用 `series_id` 串联。

### 5.2 M2 权威台账（P0）

**目的**：让这本账在争议中有唯一裁判。

**FR-2.1 公示为准的入账规则（决策 Q10-A）**

- 每个赛事每届次，由管理员批量导入主办方公示名单，一次性确认后入账。
- 不设学生个人申报入口。
- 每条入账记录强制带**证据链**：`evidence_url` 或 `evidence_file` + `verified_by` + `verified_at`。三者缺一不得置为"已确认"。

**FR-2.2 获奖记录不可变（决策 Q5-D）**

- 获奖记录一经确认即**锁定**：不允许编辑，只能"作废重开"。
- 作废需填写作废原因，原记录保留为 `status=voided`，历史可查。

**FR-2.3 线索池（对公示制漏报的补偿）**

- 学院或教师可提交"疑似获奖线索"（赛事名、赛年、项目、佐证材料）。
- 线索**不入账本**，只进管理员待办；管理员核实后决定是否走补录通道。
- **验收**：提交一条线索 → 管理员待办可见 → 处理后可追溯处理人。

### 5.3 M3 人员变更追溯与异常核实（P0）

**FR-3.1 版本快照**

- 项目成员与指导老师每次变更生成快照：`version_no`、变更前后成员集合、变更时间、发起人、变更说明、佐证附件。
- 项目全貌页提供**版本时间线**，可回放任一历史版本。

**FR-3.2 自动标红规则（决策 Q9-D）**

| 规则 ID | 规则 | 触发条件 |
|---|---|---|
| R1 | 一人多队 | 同一学号在同一赛年出现在 ≥3 个项目中 |
| R2 | 成员数超限 | 团队人数超出该赛事规则上限 / 低于下限 |
| R3 | 指导老师超编 | 指导老师数 > 规则上限 |
| R4 | 同名不同号 | 姓名相同但学号不同，且出现在同一项目 |
| R5 | 获奖后突击换人 | 获奖公示日之后发生成员变更 |
| R6 | 跨院归并冲突 | 同一项目被两个学院分别上报 |

- 命中异常 → 进入**待核实池**，每条异常必须填写处置结论：`确认无误 / 已更正 / 无法追溯`。
- 处置率作为数据质量指标在看板展示（S4）。

### 5.4 M4 看板与学院排行（P0）

**FR-4.1 总览看板**
- 核心指标：参赛项目数、参与人数、学院覆盖率、获奖数（分等级）、同比环比。
- 全部指标支持下钻至项目列表，再下钻至项目全貌。

**FR-4.2 学院排行（决策 Q16-B）**

- 折算分规则（可在后台配置）：赛事等级（国赛/省赛/校赛）× 奖项等级（特/一/二/三/优胜）× 系数。
- 每个学院的分数**必须可解释**：点开可见"哪几个项目、什么奖项、各项加了多少分"。
- 同分处理规则需在文档中明示（如按国家级奖项数优先）。

**FR-4.3 数据质量页**

- 展示：异常总数、待核实数、处置率、各来源通道数据量占比。

### 5.5 M5 AI 站内咨询（P0，V2 交付）

**FR-5.1 知识来源三层（决策 Q12-C）**

| 层 | 内容 | 维护方式 |
|---|---|---|
| L1 权威文件 | 历年通知、评分细则、管理办法、参赛手册 | 管理员上传，系统解析分块入库 |
| L2 人工 FAQ | 老师高频问题的标准答案 | 管理员维护 |
| L3 盲区挖掘 | 系统从真实问答中识别"答不上来"的问题，生成候选 | 人工确认后入 L2 |

**FR-5.2 出处强制（硬约束）**

- 每条回答必须返回：文件名、章节/页码、生效赛年。
- 无法定位出处时，**不回答**，改为转人工：显示赛事办联系人与值班时间。

**FR-5.3 赛年优先**

- 同一问题存在多赛年答案时，默认取**最新生效赛年**，并明示"该答案适用于 2026 赛年；如需 2025 口径请切换"。

### 5.6 M6 材料规范性检查与诊断（P0，V2 交付）

**FR-6.1 双引擎分工（决策 Q13-C 的工程落地）**

| 引擎 | 负责 | 特性 |
|---|---|---|
| 规则引擎 | 页数、字数、章节完整性、文件格式、命名规范、图文引用一致性 | 确定性、可解释、离线可用 |
| 模型引擎 | 解释规则、指出改写方向、分维度强弱评级 | 概率性、必须挂依据、不参与硬判定 |

**FR-6.2 输出的三道保险**

1. 显著位置声明："本报告为规范性自查建议，非评审结论，不代表任何评分或名次。"
2. 每条结论附依据（规则条款号 / 评分细则条目），无依据不出结论。
3. 上传即提示"可能含商业敏感信息"，提供"仅本地检测、不入库"选项。

**FR-6.3 诊断输出结构**

- 硬性不合规清单（✗）：逐条 + 依据 + 修改建议
- 分维度强弱（⚠）：创新性 / 商业性 / 团队 / 社会价值 / 材料规范，各给等级与理由
- **短板排序**：最该优先补的三块，按影响度排序
- 不出现：分数、名次、通过率预测

### 5.7 M7 过程模块（P2，V3）

以下功能在本 PRD 中完整定义，但排在 V3，首期不开发：

- **FR-7.1 通知与节点聚合**（决策 Q6）：AI 解析通知原文生成节点草稿 → **强制人工校对闸门** → 发布；无原文走手工录入（A 通道）。不做往届模板自动匹配。
- **FR-7.2 组队招募聚合**：同步青创珈X 招募信息，站内呈现与检索。
- **FR-7.3 自定义表单引擎**：管理员拖拽建表单、任务下发、回收、一键导出。
- **FR-7.4 推荐上报**：从校赛结果生成省赛/国赛推荐名单，按报送模板导出。
- **FR-7.5 AI 打磨反馈**：结合评审维度给作品改进建议（与 M6 共用引擎）。

### 5.8 M8 账号、权限与审计（P0）

- 自建账号库：手机号/邮箱 + 密码，支持微信扫码绑定；管理员审核制注册。
- 两类角色（管理员/普通用户），中间不设层级（决策 Q3-D）。
- 预留 SSO 适配层：`AuthProvider` 接口 + `users.external_id` 字段 + 双模式开关。
- **全量审计日志**：谁在何时改了哪条数据、发布了哪个赛事结果、处置了哪条异常。

## 6. 关键交互流程

### 6.1 赛事结果入账（主流程）

```
管理员登录 → 选择赛事与赛年 → 上传公示名单/或触发接口同步
   → 系统校验（模板/重复/人员/赛年）→ 逐行报错
   → 确认入账（生成不可变记录 + 证据链）
   → 触发异常规则 R1–R6 → 命中项进待核实池
   → 管理员处置异常（确认无误/已更正/无法追溯）
   → 一键"发布结果" → 对普通用户可见（此前仅管理员可见）
   → 看板与学院排行实时更新
```

### 6.2 项目全貌查询（学生与教师主路径）

```
搜索项目名/学生姓名 → 结果列表（含赛年、赛事、获奖等级）
   → 项目全貌页：基本信息 / 各赛段记录 / 成员版本时间线 / 获奖证据链
   → 查看历史版本（回放）
```

### 6.3 材料自查（学生主路径）

```
上传文件（或粘贴文本）→ 选择赛事与赛年 → 规则包加载
   → 规则引擎硬检查（秒级，离线可用）
   → 模型引擎分维度诊断（数秒至数十秒）
   → 输出：不合规清单 + 分维度强弱 + 短板排序 + 修改建议
   → 可选：下载报告 PDF / 仅本地检测不留存
```

### 6.4 咨询（学生主路径）

```
提问 → 意图识别（规则/流程/材料/技术/其他）
   → 检索 L1/L2 → 命中：回答 + 出处 + 赛年
                → 未命中：转人工（显示联系人）
   → 未答问题进入 L3 候选池 → 管理员确认后沉淀为 FAQ
```

### 6.5 状态机：获奖记录

```
draft(导入草稿) → verified(已核验，锁定) → published(已发布)
                        ↓
                     voided(作废，需原因，保留留痕)
```

### 7.1 核心实体

### 7.2 数据质量规则（写进数据层，不靠人工自觉）

1. 任何 `award_record` 无 `verified_by` 不得进入 `verified`。
2. 任何统计查询必须带 `competition_year`，禁止跨年缺省聚合。
3. 同一 `student_no` 在同一赛年在 ≥3 个项目 → 自动标红。
4. 成员变更发生在获奖公示日之后 → 自动标红。
5. 数据删除一律软删（`status=deleted`），不物理删除。

### 7.3 存储与迁移（决策 Q18-D 先云后迁）

- 首期：云服务器 + 云数据库 + 对象存储，容器化部署（Docker Compose 起步）。
- 迁移就绪要求：
  - 镜像内零硬编码（地址/密钥/域名全走环境变量）；
  - 存储抽象层（本地/S3 兼容对象存储可切换）；
  - 数据库迁移脚本版本化管理（如 Prisma Migrate / Flyway）；
  - **上线前完成一次完整迁移演练**，作为 S8 验收项。
- AI 侧双路径：云上可调外部 API 验证效果；迁回校内后切私有模型（如 Qwen 系列），两套共用同一提示词与评估集。

## 8. AI 设计要点

### 8.1 可解释性是第一原则

- 咨询：答必带出处（文件 + 章节 + 赛年），无出处即转人工。
- 诊断：结论必挂依据（规则条款 / 评分细则条目），硬判定只出自规则引擎。
- 界面：AI 输出统一标注"AI 生成，仅供参考"，与人工确认数据视觉区分。

### 8.2 混合架构（规则 + 检索 + 生成）

```
用户输入 → 意图路由
   ├─ 硬规则类（页数/格式/章节）→ 规则引擎直接判定（确定性）
   ├─ 事实类（规则原文、时间节点）→ 检索（RAG）→ 生成带出处答案
   └─ 判断类（创新性弱在哪）→ 检索细则 → 生成建议（必须引用条款）
```

### 8.3 评估与迭代

- 建立 50–100 题的**黄金测试集**（含易错问题、边界问题、无答案问题）。
- 每次换模型/改提示词，必须跑一遍测试集，通过率不得下降；无答案问题的"转人工率"应 ≥90%（说明不乱编）。
- 定期抽样人工复核（每周 20 条），复核结果回填知识库。

### 8.4 合规

- 不上传含身份证号、银行账号的文件进入模型上下文（前置正则清洗）。
- 材料检测提供"不入库"模式：文件只在内存/临时目录处理，处理完即删。
- 留存策略明示：默认不留存原文，仅留存结构化检查结果（可配置）。

## 12. 风险与待确认事项

### 12.1 已识别风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 两平台接口长期拿不到 | 数据永远 T+1、可信度打折 | Q4 分层降级已内置；导入通道必须打磨得足够好用 |
| 极简权限遇到跨院敏感数据 | 争议时无授权手段 | 白名单 + 结果发布开关 + 字段遮蔽；**列入待确认** |
| 云上数据出校不合规 | 落地被卡 | Q18 先云后迁 + 迁移演练；上线前完成安全评估 |
| 校内私有模型能力不足 | AI 体验下降 | 规则引擎保底 + 检索式问答降级；外部 API 走审批 |
| 5 人团队 6–8 周一期 | 延期 | 每期只压 P0；V3 允许顺延 |
| 咨询量不足导致 L3 盲区挖掘空转 | 机制成摆设 | 首期不依赖 L3，先靠 L1+L2；咨询量 ≥200 次后再启用 |
| AI 诊断引发"能不能上奖"的期待 | 信任崩塌 | 三道保险强制；UI 层禁止分数/名次表述 |

### 12.2 待确认事项（需发榜方或指导教师确认）

1. **学校语境确认**：是否确为武汉大学（第二课堂学分体系、统一身份认证平台、校院两级团委分工）。
2. **接口可行性**：第二课堂与青创珈X 是否愿意提供只读接口/数据库视图，排期如何。
3. **权限红线**：极简权限模型下，是否确有必须隔离的数据（如未公开评审意见、企业命题赛商业计划书）。
4. **统一身份认证**：落地期能否拿到 OAuth 应用；若只能部分院系，是否接受双模式并行。
5. **AI 算力政策**：校内是否允许调用外部大模型 API；若不允许，校内是否有可用的 GPU 资源与模型服务。
6. **交付边界**：本次是否需附原型/演示脚本（当前 PRD 按"含演示脚本"准备）。
7. **榜单要求核对**："智能体、工作台、数据看板"三件交付，当前 V1+V2 已覆盖，是否需要额外的独立 App 或小程 序。
8. **赛事锁定**：V1 完成后用于真实验证的具体赛事与配合老师。
