## 1. 连上去，先勘察现状（只读，什么都别改）

```bash
ssh root@8.148.76.12
```

**1.1 看目录形态**——判断是不是 release 软链布局：

```bash
ls -la /srv/kesai/
readlink -f /srv/kesai/current
```

**1.2 看三样数据在哪**（本步最关键，决定后面怎么搬）：

```bash
ls -la /srv/kesai/current/public/ | grep -i uploads
ls -la /srv/kesai/current/prisma/  | grep -iE 'db|migration'
ls -la /srv/kesai/current/.env
```

判断标准：

| 现象 | 含义 | 后面怎么做 |
|---|---|---|
| `.env` / `dev.db` / `uploads` 是**软链**（`->` 指向 `/srv/kesai/shared/...`） | 已经很规范 | 跳过第 3 步 |
| 它们是**真文件 / 真目录** | 数据躺在代码目录里 | **必须先做第 3 步**，否则下次部署就丢 |

**1.3 看当前跑的是哪个提交**：

```bash
cd /srv/kesai/current
git rev-parse --abbrev-ref HEAD    # 记下分支名，后面 pull 要用对
git log --oneline -3
git status --short                  # 必须是空的；有改动说明服务器上有本地修改
```

> 记下这个分支。如果服务器拉的不是 `main`，第 5 步的 `git pull` 要换成那个分支。

**1.4 看进程怎么起的、谁在监听**：

```bash
ps -eo pid,cmd --sort=start_time | grep -Ei 'node|next|pm2' | grep -v grep
systemctl list-units --type=service --state=running | grep -Ei 'kesai|next|pm2|nginx'
ss -tlnp | grep -E '3000|443|80'
```

**1.5 看反代、证书、时区、磁盘**：

```bash
nginx -v 2>&1 | head -2
ls /etc/nginx/sites-enabled/
grep -r "proxy_pass\|X-Forwarded-Proto" /etc/nginx/sites-enabled/ 2>/dev/null
timedatectl | head -3
df -h /srv | tail -1
```

## 2. 备份（这一步别省）

```bash
STAMP=$(date +%F)
mkdir -p /srv/kesai/backup/$STAMP

# 三样不能丢的东西
tar czf /srv/kesai/backup/$STAMP/env-db-$(date +%H%M).tgz \
  -C /srv/kesai/current .env prisma/dev.db 2>/dev/null

tar czf /srv/kesai/backup/$STAMP/uploads-$(date +%H%M).tgz \
  -C /srv/kesai/current/public uploads 2>/dev/null

# 如果已经有 storage/sealed
tar czf /srv/kesai/backup/$STAMP/sealed-$(date +%H%M).tgz \
  -C /srv/kesai/current storage sealed 2>/dev/null

ls -lh /srv/kesai/backup/$STAMP/
```

判断标准：三个 tgz 都在，且 `uploads` 那个不为 0 字节。

> **额外强调**：把 `.env` 里的 `FIELD_ENCRYPTION_KEY` **单独抄一份到别的地方**（密码管理器/纸质）。
> 这个 key 丢了，库里所有身份证、银行卡**永久解不开**，备份也救不回来。
> 而且**不要**把它和数据库备份放在同一个地方。

## 3. 数据隔离与软链（只在第 1.2 步判定"是真目录"时做）

目的：让代码更新时**碰不到**数据。

```bash
cd /srv/kesai/current

# 3.1 建持久化目录
mkdir -p /srv/kesai/shared/env /srv/kesai/shared/db /srv/kesai/shared/uploads /srv/kesai/shared/sealed

# 3.2 把数据移出去
mv .env                        /srv/kesai/shared/env/.env
mv prisma/dev.db               /srv/kesai/shared/db/ 2>/dev/null
mv public/uploads/*            /srv/kesai/shared/uploads/ 2>/dev/null
mv public/uploads/sealed/*     /srv/kesai/shared/sealed/ 2>/dev/null

# 3.3 用软链接回来
ln -sfn /srv/kesai/shared/env/.env  .env
ln -sfn /srv/kesai/shared/db/dev.db prisma/dev.db
rmdir public/uploads 2>/dev/null; ln -sfn /srv/kesai/shared/uploads public/uploads
ln -sfn /srv/kesai/shared/sealed    storage/sealed

# 3.4 核对
ls -la .env prisma/dev.db public/uploads storage/sealed
```

判断标准：四条都显示 `->`，且目标存在。

## 4. 盖章件迁移（**必须与第 5 步的 `git pull` 同一批**）

新版本把盖章件从 `public/uploads/sealed`（能被静态直链访问）搬到了 `storage/sealed`（只有鉴权接口能读）。

```bash
cd /srv/kesai/current
mkdir -p storage
# 老文件搬过去（如果第 3 步已经做过，这步会提示无文件，正常）
mv public/uploads/sealed/* storage/sealed/ 2>/dev/null
rmdir public/uploads/sealed 2>/dev/null
ls -R storage/sealed | head -20
```

⚠️ **只做一半会出事**：

| 只做了一半 | 后果 |
|---|---|
| 只上代码、不搬文件 | 老盖章件全部 **404**，学生和审核人打不开 |
| 只搬文件、不上代码 | 新上传仍写回 `public/uploads/sealed`，**安全洞照旧** |

## 5. 拉代码 + 依赖 + Prisma 引擎

```bash
cd /srv/kesai/current

git fetch origin
git pull --ff-only origin main          # 若第 1.3 步发现分支不是 main，换成实际分支

npm ci                                  # 不要用 npm install，锁版本更稳
npx prisma generate                     # 必须在 Linux 上跑，不能用 Windows 产的引擎
```

判断标准：
- `git pull` 是 fast-forward，没有冲突
- `prisma generate` 输出 `Generated Prisma Client`
- **不要**在服务器上跑 `npm run db:seed` / `demo:*`——那会灌演示数据，覆盖真实数据

如果 `npm ci` 报错，先看是不是 Node 版本问题：`node -v` 应为 22.x。

## 6. 数据库迁移：已有数据的旧库要"登记基线"

**这一步是最容易挂的地方。**

你的库是之前用 `prisma db push` 建的：有 32 张表、有真实数据，但里面**没有** `_prisma_migrations` 表。
而仓库里新增的基线迁移 `20261113000000_init` 是一份**全量 `CREATE TABLE`**。

所以：

```bash
npx prisma migrate status
```

| 输出 | 含义 | 该做什么 |
|---|---|---|
| `Database schema is up to date` | 已登记过 | 跳过，进第 7 步 |
| `20261113000000_init` 是 pending / `0 migrations have been applied` | 没登记过 | **走下面（不要 deploy）** |

```bash
# 只往 _prisma_migrations 里写"已应用"，不动任何表和数据
npx prisma migrate resolve --applied 20261113000000_init

npx prisma migrate status     # 复查，应显示 up to date
```

❌ **绝对不要**在已有数据的库上执行：

- `npx prisma migrate deploy`（会尝试重放 `0_init` → `Error: table 'User' already exists`）
- `npx prisma migrate reset`（**会清空整个数据库**）
- `npx prisma db push --force-reset`（同样清库）

> 如果是**全新的空服务器**（库里一张表都没有），那就反过来：直接 `npx prisma migrate deploy` 建表，然后按需导入数据，**不要**用 `db push`。

## 7. 构建与重启

```bash
cd /srv/kesai/current
npm run build
```

**判断标准**：最后出现路由表 + `Middleware`，且没有 `Failed to compile`。

**构建失败要立刻回滚代码，不要重启服务**（旧进程还在跑旧代码，能继续服务）：

```bash
git reset --hard ORIG_HEAD      # 回到 pull 之前那个提交
npm ci && npx prisma generate && npm run build
```

构建成功后再重启：

```bash
systemctl restart kesai
# 或者用 pm2：pm2 restart kesai
systemctl status kesai --no-pager | head -15
```

如果服务还没被 systemd 托管（`systemctl status kesai` 说不存在），见第 8 步；临时可以先手动跑：

```bash
cd /srv/kesai/current && npm run start
```

## 8. 进程托管（只做一次）

`/etc/systemd/system/kesai.service`：

```ini
[Unit]
Description=Kesai competition platform
After=network.target

[Service]
Type=simple
WorkingDirectory=/srv/kesai/current
Environment=NODE_ENV=production
Environment=PORT=3000
Environment=TZ=Asia/Shanghai
ExecStart=/usr/bin/npm run start
Restart=always
RestartSec=5
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now kesai
systemctl status kesai --no-pager | head -15
journalctl -u kesai -n 50 --no-pager      # 看日志
```

> 时区必须是 `Asia/Shanghai`。虽然业务格式化代码里已硬编码时区，
> 但日志时间戳和定时任务要靠环境变量，UTC 会让你排查时差 8 小时。

## 9. Nginx 与 HTTPS（只做一次）

`/etc/nginx/sites-enabled/kesai.conf` 关键片段：

```nginx
server {
    listen 443 ssl http2;
    server_name your.domain.com;          # 现在是裸 IP，就写 IP

    ssl_certificate     /etc/nginx/ssl/kesai.crt;
    ssl_certificate_key /etc/nginx/ssl/kesai.key;

    client_max_body_size 25m;             # 盖章件上限 20MB，留余量

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;   # ← 漏了这行 Cookie 会掉 Secure
        proxy_set_header Upgrade           $http_upgrade;
        proxy_set_header Connection        "upgrade";
    }
}
```

```bash
nginx -t && systemctl reload nginx
```

**两个顺序不能反的事**：

1. **先装有效证书，再绑域名。** HSTS 对裸 IP 会被浏览器忽略（RFC 6797），所以现在拿 IP 访问没问题；
   但一旦绑了域名而证书还是自签的，HSTS 会让浏览器**直接拒绝访问，连"继续前往"都没有**。
2. **先打通 HTTPS，再验登录。** `next start` 会设 `NODE_ENV=production`，Cookie 带 `Secure`；
   用明文 `http://IP:3000` 访问时浏览器会拒收这个 Cookie，表现是「登录返回 200，但页面还是登录页」。

## 12. 故障排查

| 现象 | 最可能的原因 | 处理 |
|---|---|---|
| 登录返回 200 但仍在登录页 | 明文 HTTP 下 Cookie 被拒收 | 用 HTTPS 访问；确认 Nginx 传了 `X-Forwarded-Proto` |
| 盖章件下载 404 | 文件没搬到 `storage/sealed` | 回到第 4 步 `mv`，然后 `systemctl restart kesai` |
| 盖章件静态链接能直接打开 | 代码没上新版 / `storage/sealed` 软链指错了 | 检查 `readlink storage/sealed`，确认在 `public/` 之外 |
| `prisma migrate deploy` 报 `table 'User' already exists` | 已有库没登记基线 | 第 6 步 `migrate resolve --applied` |
| 页面 500 且日志有 `ENOENT vendor-chunks/...` | `.next` 缓存损坏 | `systemctl stop kesai && rm -rf .next && npm run build && systemctl start kesai` |
| `prisma generate` 报 `EPERM rename query_engine` | 有进程占着引擎文件 | 先 `systemctl stop kesai` 再 generate |
| 磁盘满 | `storage/imports/` 堆积 | 已有 7 天自动清理；手动 `find storage/imports -mtime +7 -delete` |
| 提示"尝试次数过多" | 登录限流触发（15 分钟窗口） | 等 15 分钟，或 `systemctl restart kesai`（限流是内存态，重启即清空） |
